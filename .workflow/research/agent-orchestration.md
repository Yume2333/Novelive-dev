# Research: Novelive Agent 编排

Novelive Agent 的角色、编排、上下文、预设和对话面板。下面的方案已和所有者逐项确认；还没定的放在末尾“Open questions”。调研依据是 wenyi、Luker、pi 1.5.2 源码、SillyTavern，以及几个生图库和对话前端库，调研报告原文在 `refs/`；pi 部分已按 1.6.0 复核（`pi-scaffolding.md`）。各阶段的输入输出细节见 `novelive-agent.md`，两份文件冲突时以本文为准。

## Settled & ruled out

- **pi 用到哪一层**：
  - `pi-ai`：各种接口格式、流式事件（正文、思考、工具参数增量都有）、用量和费用、取消、上下文溢出检测 `isContextOverflow`、采样参数 `samplingParams`、`constrainedSampling`。
  - `pi-agent-core`：`Agent` 循环、工具执行、事件，以及 `transformContext` / `prepareRequest` / `prepareNextTurn` / `beforeToolCall` / `afterToolCall` 这几个钩子。
- **pi 没有的、我们自己做**：会话存储、上下文压缩、子 Agent、按角色选模型、写手预设、运行记录。`pi-durable` 有现成实现但标实验性、API 随版本改，我们照它的设计自己写（见 `decisions.md` 2026-11-21「编排继续用 pi-agent-core」）。
- **不依赖 `pi-coding-agent` 包**：它是 CLI 的 SDK，带 `~/.pi` 目录约定、同步文件写入和一串 CLI 依赖。它是 MIT 许可，我们照着它的思路移植两样东西：
  - 上下文维护：只用于对话面板和美术导演的长循环，分清理 → 抖掉 → 摘要三级（决策 2026-11-21「上下文维护分级」），摘要模型可用上下文更大的已配置模型；机制与阈值全文在 `pi-scaffolding.md` 通用层 6，本文不重复。
  - 会话条目树：`id` / `parentId`、压缩摘要条目、分支摘要条目；条目类型含 `session_init`（完整 spawn 输入落盘）、`system`（系统提醒，进模型前转 developer 消息）、`idle`（轮次边界）、`custom`/`model_usage`（转录外记账）。
- **生图调用用 `openai` 官方 SDK**：只有它同时支持多张参考图编辑、透明底、任意尺寸和生成中的预览流，还能用 `code === 'moderation_blocked'` 识别审核拒绝。不用 Vercel AI SDK（没有预览流），也不用裸 `fetch`。
- **对话前端用 `assistant-ui` 加 `streamdown`**：
  - `assistant-ui` 是 MIT 许可的无样式组件库；runtime 用 **ExternalStoreRuntime + `messageRepository`**——我们的会话本来就是 `id`/`parentId` 条目树存 `project.db`，形状一一对应，创作端是唯一事实源，UI 只做投影（喂进的消息要过 `fromThreadMessageLike` 归一化）。不用 LocalRuntime（一问一答表达不了 park 等确认卡和后端改历史），也不用 AssistantTransport（HTTP/SSE 语义强套 MessagePort）。`@assistant-ui/react-pi`（MIT）是给 pi-coding-agent 写的同款适配层，投影和 approval 映射的思路直接参照。
  - `streamdown` 负责流式 Markdown（不启用 KaTeX/mermaid 插件，剧本和讨论用不上）。
  - 不用 Vercel AI Elements：它绑死 Tailwind 和 AI SDK，而且即将弃用。
- **不学酒馆的完整预设体系**：酒馆的提示块排序、按深度注入、世界书、导入酒馆预设都不做。原因有两个：跑在 pi 上做不到和酒馆一样；随意插入的内容会破坏提示缓存。
- **给模型的工具一律封装成一步到位的动作**：模型只给它擅长的东西（画面描述、要改的文字、判断和理由），机械的部分全在工具里由代码做：接口参数、尺寸、透明底、参考图怎么传、文件路径、格式转换、ID 分配、检查和重试。例如画师只有 `draw_image { content }`：要画哪张图由代码绑定，工具内部按素材类型定尺寸和背景、取参考图、选生成或编辑接口、调接口、做技术检查和视觉审核、存文件，只把“通过”或“不通过和原因”交回；不让模型拼一长串参数或连续调几个底层接口。一件事一个工具，不做靠 `kind` 字段切换的万能工具。每加一个工具都按这条检查：模型要填的参数里不能有代码能算出来的东西；代码已知的材料直接放进上下文，不另做查询工具。

## 1. 模型与角色

设置里配五个模型：**快速、主模型、写作、视觉、图片**。每个角色有默认对应的模型；高级设置里可以单独给某个角色换模型。

| 角色 | 默认模型 | 形态 | 负责 |
| --- | --- | --- | --- |
| 整理 | 快速 | 单次调用 | 逐章预览、卷内摘要汇总、导入时核对章节和作品信息、会话标题、压缩摘要、把修改总结成规则 |
| 主控 | 主模型 | 工具循环 | 按卷综合（提取设定）、设定冲突说明、对话面板的 Agent |
| 写手 | 写作 | 单次调用，不用工具 | 写剧本：台词、旁白、内心独白、字幕，以及谁上场、用什么表情；自己分场 |
| 美术导演 | 主模型 | 工具循环 | 读整章剧本，补背景、镜头、CG、粒子和滤镜等演出；列出本章要用的图清单，做同义表情合并 |
| 立绘画师 | 主模型 | 工具循环 | 画造型基准图：参考角色设定图（或上一套造型）重画，竖版透明底 |
| 场景画师 | 主模型 | 工具循环 | 画背景基准图和 CG：16:9，主体落在中间 4:3 安全区 |
| 差分画师 | 快速 | 工具循环 | 画表情差分和背景变体：从基准图编辑派生，只改一处 |
| 视觉审核 | 视觉 | 单次调用 | 在生图工具内部看图，核对身份、锚点（含 `keyColors`）、描述（含剧情要点）、画风、瑕疵五项 |
| 审稿 | 主模型 | 工具循环 | 分两档（决策 2026-11-21「审稿拆成忠实度检查和文风审稿」）：忠实度检查默认开，只查漏段、加戏、对白改写、说话人归属错、独白降级、顺序不连贯、设定冲突，每条问题必须引用原文段落、由代码核对引文确实在原文里；文风审稿是作品开关、默认关，只评文笔不评情节结构。都用工具按需查证据（原文段落、术语出现位置、章节摘要），都不循环：写手按问题改一遍，不再复审 |

- 写手不用工具。很多擅长写作的模型工具调用能力弱，所以材料由代码准备好送进去。
- 除写手预设外，其他角色的提示词都内置，不开放修改。用户想影响它们，就写进作品的改编要求和规则。
- 只有主控能派子 Agent，子 Agent 不能再派。

## 2. 制作流程

**整体顺序由代码调度**：逐章预览（可并行）→ 按卷综合 → 确认点 1 → 按章制作 → 确认点 2 → 后续章节。立即停止、重跑被中断的任务、制作面板的进度，都建立在这一层的确定步骤上。

**一章三步加一个出图阶段：写、审稿（忠实度检查默认开，文风审稿可开）、演出与图清单，然后按素材队列出图**，每步做完都把结果存下来，停下后从没做完的那一步接着做：

1. **写**（写手）：一章调用一次。写手自己分场，每场写上场景标题和对应的原文段落范围。章太长时，代码按段落切成几段依次写，后一段会带上前一段剧本的结尾。代码负责解析剧本和分配 ID；剧本不通过检查时走剧本检查与局部修复，只把出错的场景退回写手改。
2. **审稿**（分两档）：忠实度检查默认开，对照原文和设定集只列有把握的问题，每条必须引用原文段落并由代码核对引文确实在原文里；文风审稿是作品设置里的开关（默认关），只评文笔。两档都是：问题定位到句子，写手按这些问题改一遍，改完不再复审。剧本定稿后才进演出，避免返修让已画的图对不上。
3. **演出与图清单**（美术导演）：一章跑一个工具循环。美术导演默认读整章剧本（实测整章模式的 token 花费和补丁格式合规率都优于分批；只有整章放不进上下文时才按场景分批读入、分批插演出，并配一层补丁格式规范化），用补丁工具插入演出指令——补丁是带行号视图的行锚点格式（插入、替换、删除三类操作，参数就一个字符串，决策 2026-11-21「调研后的取舍」），解析器校验、错了退回；编辑器的场景重写仍用整段新文本加句子 ID 差异。然后列出本章要用的图清单：每项填素材名、类型、一句描述；已有还是新画由代码按素材名和已登记素材判定，模型不填。列清单时做同义表情合并：写手写出的未登记表情先和已有表情比对，意思相同就改用已有的。要新画的图进入出图队列。
4. **出图**（三个画师，由代码按出图队列调度）：队列按素材排，同一张图只画一次；基准图画完，从它派生的差分才开始画；一章要用的图都齐了这章就发布。每个画师各有内置提示词和检查重点，自己调用生图工具：工具内部依次做出图 → 本地技术检查 → 视觉审核，把“通过”或“不通过和原因”交回画师，由它决定要不要换提示词重画；重画次数用完「生图失败重试次数」（默认 3）就用占位图并标“需要处理”。同时画的图不超过设置里的「同时出图数」（默认 8）。每张通过检查的图立即保存；停止后重跑时跳过已有的图，只补没画完的。被审核拒绝时，工具内部会先改写提示词再试一次，还拒就用占位图并标“需要处理”。

**写和画重叠**：写手写下一章时，上一章在出图。写手仍一章接一章写，衔接用上一章剧本的结尾。

**确认点让出制作槽**：作品停在确认点等创作者处理时让出制作槽，排在后面的作品先做；创作者确认后这部作品排回队首。

**制作的并发**来自角色分工和出图队列：预览可并行、三类画师按「同时出图数」并发、写和画重叠。文本调用不限并发。任务/出图队列的表结构用五张表：`work`（作品制作槽）、`task`（待做事）、`task_dep`（依赖，软依赖只在章被设为优先时可豁免）、`asset`（出图队列实体，每张图一行，重画原地复用）、`chapter`（用户看到的章状态）；预览和综合不占制作槽，对还没做完的章发起「重做本章」直接拒绝（详见 `pi-scaffolding.md` 通用层 4「任务队列」，M1a 规格定）。

**一章的基础花费**：写手 1 次（长章按切出的段数增加）、忠实度检查 1 次加写手返修 1 次、开了文风审稿再多 2 次、美术导演的一个循环、每张图画师的一个循环加 1 次视觉审核。

## 3. 上下文与长书

- **制作中的调用不累积对话**：每次调用都由代码从存好的结构化数据现拼上下文。压缩只用于对话面板的会话和美术导演的长工具循环。
- **三层摘要**：
  - 章节摘要：由整理角色做；长章先切块再合并；人名保留原文写法。
  - 卷摘要：卷内分组汇总，卷是天然的汇总边界。
  - 全书梗概：汇总到当前卷为止。
- **写手的提示顺序**，从前到后：
  1. 写手预设（文风、内置可选风格块、输出约束）
  2. 剧本格式说明
  3. 改编设置：作品级的改编强度、演出密度、改编要求、本作品规则（一卷内通常不变）
  4. 全书梗概（到当前卷为止）和本卷骨架
  5. 截至本章的设定切片：只含本章出场的人物和地点、本章原文里出现的术语、还没回收的伏笔
  6. 本章原文和上一章剧本的结尾
  7. 本次指令（含本章规则）

  写手按作者视角看第 4 项：能看到后面会写什么方便埋伏笔，提示词要求不提前揭晓；第 5 项仍严格截到本章。本章是优先章节、上一章还没写时，第 6 项的衔接改用上一章的全书预览摘要；上一章写完后不回头改。前缀保持不变，服务商支持时同一卷的各章能命中提示缓存，实际命中看用量里的缓存读取。衔接只用上一章剧本的原文（或预览摘要），不靠滚动摘要，避免越滚越偏。
- **审稿按需查证据**：审稿不读全书，用工具按需查原文段落、术语出现在哪里、某一章的摘要。
- **上下文维护**：对话面板会话和美术导演长循环按清理 → 抖掉 → 摘要三级处理，每级做完重新计量，降到触发线的 0.8 以下就停；服务商报上下文溢出时按同样顺序处理后重发一次，还溢出标“需要处理”。机制、阈值和计量公式全文在 `pi-scaffolding.md` 通用层 6。每个模型配置都要有上下文长度：pi 内置模型目录里查得到就自动填，查不到让用户填。

## 4. 写手预设

- **内容**：
  - 文风说明、输出约束：都是自由文本。
  - 内置可选风格块：视角、叙事风格、节奏、情感策略各选一项，可被文风说明自由文本覆盖。
  - 采样参数（可选）：温度等，交给 pi 的 `samplingParams`。
  - 输出替换规则（可选）：查找和替换，在解析剧本之前运行，用来清掉模型腔、修正常见格式问题。
- **位置**：放在系统提示里、剧本格式说明之后的固定位置，不随章节变化。
- **范围**：应用里有一个全局默认预设；作品可以改选别的预设，或者在默认预设的基础上改几项。

## 5. 对话面板

- **会话**：每部作品可以有多个会话，能新建、改名、删除。会话存成 `id` / `parentId` 的条目树，存在 `project.db` 里，压缩摘要也是一种条目。改写一条消息后重新发送会形成分支，可以在分支之间切换。
- **Agent 能做的事**（主控）：
  - 读工程：设定集、术语表、剧本、原文、预览、制作状态。
  - 提出修改：以确认卡的形式。
  - 发起工作流：重做章节、重写场景、重画图片、重新综合某卷。发起前先出确认卡，写清要做什么、影响哪些章节，确认后才开始。
  - 派子 Agent。
- **显示**：
  - 消息内容：流式正文、可以折叠的思考、工具调用卡片（参数随流填充，之后显示结果）、子 Agent 展开为嵌套内容、确认卡或拒绝卡、停止按钮。
  - 运行记录：制作面板里点开某一章，用同一套组件查看它的运行记录。
- **数据**：由创作端通过 MessagePort 推给界面，不走 HTTP。推送的是投影后的整条 assistant 消息快照加 headId，每 30–50ms 合一批，界面不自攒 delta；断线补漏走 `events.list` + 快照重放。确认卡用 assistant-ui 自带的工具审批（`tool-call` part 挂 `approval`、`onRespondToToolApproval` 回确认/拒绝和理由），分支切换走 `unstable_onBranchChange` 回报 headId 给创作端。面板可以贴图：创作者粘贴图片给主控看参考图，走 assistant-ui 的 attachment 接口，进 pi 的 `prompt(input, images)`。

## 6. 其他用到 AI 的地方

| 场景 | 角色 |
| --- | --- |
| 导入：核对章节划分、识别作品信息和系列卷 | 整理 |
| 确认点 1：EPUB 插图筛选 | 视觉审核 |
| 确认点 1：没有参考图时第一卷每个主要角色每套造型候选默认 3 版（主控写文字，立绘画师出图） | 主控 + 立绘画师 |
| 风格与主视觉 | 主控 + 场景画师 |

| 编辑器：单图重生成 | 对应的画师（立绘找立绘画师、背景和 CG 找场景画师、差分找差分画师；生图工具内含视觉审核） |

| 设定冲突说明 | 主控 |
