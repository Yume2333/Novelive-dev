# Research: Novelive Agent 各阶段输入输出契约

Novelive Agent 各阶段的内部结构：调用形态、上下文组装、输出契约、校验修复、持久化与停止恢复。依据 `docs/` 与 `decisions.md`；pi API 调研时依据 1.5.2 包内 `.d.ts`（见附录），已在 `pi-scaffolding.md` 对 1.6.0 复核。

> 本文是各阶段的输入输出契约；角色、流程、上下文以 `agent-orchestration.md` 为准。

## Settled & ruled out

- Agent 底座用 pi（`@earendil-works/pi-ai`、`@earendil-works/pi-agent-core` 1.6.x），作为库嵌在创作端 utility process 里。Schema 用 `@earendil-works/pi-schema`，同一份定义给代码、校验和模型。幕后数据（任务、用量、对话记录）进 `project.db`，作品内容是普通文件。
- 五个模型（快速、主模型、写作、视觉、图片）、九个角色（整理、主控、写手、审稿、美术导演、立绘画师、场景画师、差分画师、视觉审核），角色和模型的对应见 `agent-orchestration.md` §1。文本模型按接口格式（OpenAI Chat Completions / OpenAI Responses / Anthropic Messages）+ 地址 + 模型名 + Key 配置；图片模型只接 OpenAI 兼容图片接口。
- 只有两个确认点：角色设定/主视觉、第一章成品。候选设定不冲突直接用、冲突不覆盖已确认。剧本是 `.nvs` 文本，ID 由应用分配，模型不写。
- 停止只有立即停止：中断正在跑的请求，重跑被中断的任务。临时错误两层重试：第一层在我们包的 `streamFn` 里统一传 `maxRetries: 2`，管响应头到达前的失败；第二层在 `streamFn` 外包一层整条消息重发，管流到一半断开、空回复、网关返回 200 后掉线，只在这条消息还没产生工具副作用时重发，最多 2 次；流式输出加空闲超时，超时按临时错误处理；用户取消不进任何重试。图片调用用 `openai` SDK 自带的默认重试；重试用完标“需要处理”。内容审核拒绝不算临时错误、不消耗重试次数：写手那章先按降敏规则改写一次，还被拒就标“需要处理”，和图片的处理方式一样。不做防御性设计：不另做并发限制、超时、阈值。例外：出图有「同时出图数」（默认 8）和「生图失败重试次数」（默认 3）两个设置项；工具循环角色（美术导演、审稿、主控、子 Agent）设请求次数预算（占位默认：美术导演 30、审稿 20、主控 40、子 Agent 15，待测试用书到后校准），超过时插系统提醒写明已用次数、预算和硬停线，做完当前一步交结果、没做完的在结果里标出来，到 1.5 倍停掉当前轮次只留提交工具再插一条强制收尾提醒，之后 5 次请求内还没交就中止并标“需要处理”（写法照 oh-my-pi `task/executor.ts` 的 `buildBudgetNotice` 和 `prompts/system/subagent-yield-reminder.md`，MIT）；画师照旧只数重画次数。文本调用不限并发，并发来自角色分工和主控派出的子 Agent。
- 对话面板修改一律先列为待确认提议；聊天记录存工程；修改立即生效可撤销，Agent 重写场景先给差异列表。
- 不在本设计内的：联网搜图、先整本翻译再制作、作品包安全模型。

## 总体结构

- 一个 `createModels()` 持有按接口格式建的 `Provider`（`createProvider`），文本模型走 `provider.streamSimple`；图片调用绕开 pi，用 `openai` 官方 SDK，调用路径参考旧仓库 `integrations/openai-images`（补自定义地址）。图片接口的错误分类先看响应体里的错误代码（`service_unavailable`、`overloaded`、`rate_limit` 这类即使状态码是 4xx 也按临时错误处理），不只看 HTTP 状态码。
- 调用形态分两类：
  - **单次调用**：一个 `Agent` 实例跑一个 `prompt()`，系统提示给输出契约（pi-schema 定义原样序列化成 JSON Schema 进提示词），模型用纯文本回答 JSON；解析失败时 `prompt()` 再补一轮把错误还给模型。整理、写手、视觉审核走这种形态。
  - **工具循环**：`Agent` 挂一组 `AgentTool`，模型多轮读写工程。审稿、美术导演、三个画师和对话面板（主控）用：审稿要按需查证据（原文段落、术语出现位置、章节摘要）；美术导演要按章读剧本、插演出补丁；画师要拼提示词、调生图工具；主控操作面宽（查设定、读剧本、提提议），硬编码成一问一答会丢上下文。

- 工具循环角色通过 `submit_*` 工具交结果，工具的参数就是输出 schema；`finishTurn` 在没收到或校验没过时让循环继续，收到并通过校验才结束。单次调用角色维持文本 JSON 输出加校验。
- `Agent` 实例随任务创建和销毁，不跨任务复用；停止时 `agent.abort()`，pi 的 `streamFn` 透传 `AbortSignal` 到 provider，会话结束调 `cleanupSessionResources(sessionId)` 清掉 pi-ai 的会话资源。被中断的任务在 `project.db` 里保持未完成状态，继续时重跑被中断的那一步（产物中途落盘的从已落盘进度续跑，见「按卷综合」「出图」）。队列用五张表（`work`、`task`、`task_dep`、`asset`、`chapter`）管意图，`run`/`run_step` 只记事实：图片队列以 `asset` 为单位、每张图一行终身、重画时原地复用；软依赖（`task_dep.soft`）只在章被创作者设为优先时才能豁免；对还没做完的章发起「重做本章」在提议时就拒绝；预览和综合不占制作槽——「同一时间只制作一部作品」只约束章和图两类任务。
- 用量：`subscribe` 里按 `turn_end`/`message_end` 收到的 `AssistantMessage.usage` 记一条 `usage` 记录，字段 `作品 ID、阶段、任务 ID、角色、模型名、input/output/cacheRead/cacheWrite/totalTokens、cost.total、时间戳`。图片调用按次记一条。
- 写入前核对输入：写剧本、综合设定、出图这类任务开始时记下所用原文和设定的哈希，落盘前重新算一遍；变了就不写入，标“输入已改，需要重跑”。
- 工具的引用类参数（chapterId、sceneId、asset 等）第一步查存在性；不存在时错误文本回“该 ID 不存在 + 合法清单（或提示用哪个工具列出合法 ID）+ 一个正确调用例子”，教模型照着改。

## 提示词组织

- 内部提示词（系统提示、阶段指令、工具描述）用英文写，放进 `creator` 包常量。设定集/术语表/改编要求/剧本等作品数据按 `bible.md` 用作品语言；提示词里只写一句“用作品语言输出描述性文字”。
- 改编控制的注入位置：写手每个写剧本或改剧本的调用在系统提示末尾、剧本格式说明之后拼一段“改编设置”：改编强度、演出密度、改编要求原文、红线断言（违反即整章作废的可检查断言，渲染时置顶、结尾再强调一次，内容人工必审）、本作品规则（一卷内通常不变）；本章规则放进最后的“本次指令”。规则只列对当前章生效的；新规则在任务启动时快照进任务记录，做到“只影响还没开始的任务”。
- 写手的剧本格式说明包含一张原文→剧本转换判定表（照 t2vn 标注规则表翻成简中，yamasoo/text_2_visual_novel `docs/20_標註規則.md`，MIT）：引号内→对白去引号；同一段被动作分开的两截话合成一句对白，中间动作成旁白放在对白前；纯说话标记（“她说。”）删掉（VN 显示说话人名字），带情绪/动作/否定的保留成旁白或表情；原文有“她想”类标记的内心独白→主角内心独白；第三人称的心理描写标成 `(inner)` 时必须改写成第一人称，否则留作旁白；自由间接引语保留为旁白；被打断的话保留破折号；表情拿不准选较平的。
- 写手系统提示写“可知性边界”段（AI_NovelGenerator 的思路，AGPL 只参考、用自己的话写）：作者知道的秘密不等于人物已经知道；计划终点是后续边界不是本章必须提前完成的目标；已消耗的资源不能再支付；未附的全书剧情保持未知，不自行补终局；人物不得按不在 `knows` 里的信息行动或反应。
- 写手调用不重复注入全书预览和卷级设定全集；只给本章相关切片（见「上下文与长书」）。

## 上下文与长书

- `source/preview/<章节ID>.json` 是长期记忆。三层摘要：章节摘要（整理做，长章切块再合并）、卷摘要（卷内分组汇总）、全书梗概（汇总到当前卷）。
- 写手的提示顺序和切片规则见 `agent-orchestration.md` §3：截至本章的设定切片只含本章出场的人物和地点、本章原文里出现的术语、还没回收的伏笔；衔接只用上一章剧本结尾的原文（上一章未写时用其预览摘要），不靠滚动摘要。
- 设定集切片按 `bible.md` 规则过滤：`revealedChapter`（第几章揭示，M1a 起）在第 N 章之后的条目不读给模型看、“变化”只应用到 N、时间线和伏笔截到 N。过滤在组装上下文时由代码做，不交给模型判断。
- 数百上千章靠三点留在上下文内：预览逐章只存 JSON 文件按需读；综合产物（骨架、设定集）本身就是压缩形态，每章调用只带切片；衔接只带上一章剧本的结尾原文，不带整章剧本。

## 全书预览（逐章）

- **角色/模型**：整理（快速模型），单次调用。逐章一次调用，不用工具。
- **输入**：作品语言 + 本章正文。超长章节按段落切段，段间带上一段末尾若干句做衔接；每段输出同一份 schema，代码把各段结果合并成一章的条目（拼接列表、拼接摘要为分段摘要）；相邻段容易抽出语义重叠的条目，合并后加一次便宜的合并调用（或代码按段落边界去重）去掉重复条目。
- **输出契约**：`ChapterPreview`（pi-schema）：`chapterId`（代码填）、`summary`、`characters`、`locations`、`timelineNotes`、`foreshadowingHints`（只报读者看得见、但还没解释的钩子，叙述者的预示和评论不算）。ID 由应用从导入时的章节划分来，模型不写。
- **校验/修复**：JSON 解析或 pi-schema 校验失败 → 把错误文本追加为下一轮 user 消息再跑一次。
- **持久化**：写 `source/preview/<章节ID>.json`。一章一个文件，写成功即任务完成；中断的章重跑。

## 按卷综合

- **角色/模型**：主控（主模型），单次调用。一卷一次或分块调用，输出结构化条目，不逐章对话。卷太长放不下时先试“每次抽下一个事件”的做法（ViMax 式：全文或卷内预览加上已抽事件列表，每次只抽下一个事件，模型自报 `is_last`，代码设硬上限防死循环；产物中途落盘可续跑）——先用测试用书验证，不好用再退回按章数分块先做中段摘要再合并。
- **输入**：本卷各章的 `ChapterPreview` 全文（摘要级，不是原文）、上一级（系列/卷）已有的设定集和术语表、作品语言、改编要求。
- **输出契约**：三个产物。
  - `VolumeSkeleton`：本卷主线概要文本 + 分章一句话进度。
  - `BiblePatch`：角色/关系/地点/时间线/伏笔/风格的条目列表；每条逐条标 `op: "add" | "update" | "delete" | "none"`（update 带它要更新的旧条目 ID；`delete` 只在同一卷综合时用来纠正误建的条目，导入新一卷加入已有系列时只用 `add | update | none`，不删系列已有条目），另带 `status: "candidate" | "confirmed"`（模型建议）、`firstSeenChapter`、`revealedChapter`（第几章揭示，M1a 起；原文引文证据 `evidence[].quote` 到 M2 再加）、`knows`（角色第几章知道了什么）、字段内容、`changes` 列表。字段分两类：“固定”字段（发色、本名这类不会变的）和“会变”字段（身份、职位这类随剧情变的），会变字段出现不同值记成变化、不报冲突，固定字段不同值才算冲突。
  - `GlossaryPatch`：术语条目列表（原文写法、作品写法、注音、类别、备注）。
- **校验/修复**：pi-schema 校验；`firstSeenChapter` 必须是本卷章节 ID，引用关系（变化指向的条目 ID）由代码核对，不存在的引用当错误还给模型。
- **冲突规则在代码里**：应用侧合并时，候选条目和已确认条目同 ID 且“固定”字段冲突 → 保留已确认版本，冲突条目仍写进文件标 `candidate` 加冲突说明；“会变”字段出现不同值记成变化、不阻塞也不覆盖；不冲突的候选直接可用。模型只负责提条目，合并逻辑不在模型侧。
- **别名合并在代码里**：同一章内先按规则挡（字符子串包含、姓氏+单名规则、章窗口、称谓停用词、候选唯一，全满足才并）；规则挡不下的跨章变体交模型裁决，默认不合并。身份类（马甲/转世/真名揭示）不合并成一条，记成带 `revealedChapter` 的“同一人”关系，设定集切片按章决定显示哪个名字。
- **持久化**：骨架写 `volumes/<卷>/bible/skeleton.json`；条目按层级写进 `bible/`、`glossary.json` 文件。任务粒度到卷，产物中途落盘，中断后从已落盘进度续跑、不整卷重头（流式抽取做法下已抽的事件列表就是进度）。

## 确认点 1：角色设定候选

- **EPUB 插图筛选**：视觉审核（视觉模型），单次调用。输入是 EPUB 抽出的插图二进制 + 角色条目（名字、外貌描述），输出 `IllustrationPick[]`：每张图给 `characterId`、`lookHint`（哪套造型）、`reason`。模型只看图和文字，不改写设定。
- **无参考生成设定**：主控（主模型）+ 立绘画师，文字和图各出 3 版，只针对第一卷的主要角色；其余角色第一次出场时由立绘画师按设定集描述直接画造型基准图，不停下确认。主控按角色条目里的外貌、身份字段写 3 版不同的外貌描写和造型建议，立绘画师写内容段、调用生图工具出图。确认后选中的版本写回 `bible/characters/<角色>.json` 的外貌和造型字段。
- **持久化**：筛选出的插图复制到 `candidates/`；提议存 `project.db` 的提议表（见对话面板），确认后落文件。确认点本身只是“等创作者处理”，不在 Agent 内阻塞；Agent 任务到产出候选就结束。

## 写剧本（一章）

- **角色/模型**：写手（写作模型），单次调用，不用工具。一章调用一次；写手自己分场，每场写上场景标题和对应的原文段落范围。章太长时，代码按段落切成几段依次写，后一段带上前一段剧本的结尾。提示词里写明「每段恰好覆盖一次」；代码按段落范围核对覆盖（`coverage_report`），出现缺漏或重叠时把「缺 p0007–p0011」这类诊断交回写手，和剧本检查走同一条路。
- **输入**：写手预设和剧本格式说明（系统提示固定位置）、改编设置、全书梗概和本卷骨架、截至本章的设定切片、本章原文、上一章剧本的结尾、本次指令和本章规则。顺序见 `agent-orchestration.md` §3。写手按作者视角看全书梗概（到当前卷）和本卷骨架，提示词要求不提前揭晓；优先章节的上一章还没写时，衔接改用上一章的全书预览摘要。
- **输出契约**：整章 `.nvs` 剧本文本。场景头 `scene` 标题和 `source` 原文段落范围由模型写；应用只核对 `source` 指向本章里存在的段落，不生成。句子 ID 由应用保存时补 `#xxxx`；模型也可以在 `@show` 里直接用未登记表情名，应用解析后补登记。
- **校验/修复**：剧本检查与局部修复。`.nvs` 解析器给出带错误码和位置的诊断；代码先修代码块围栏、BOM、换行这类机械问题，再查素材名、原文段落范围、句子 ID；只把出错的场景退回写手改，不整章重写。这是 `work-format.md` 里「解析与模型输出」的落地。
- **持久化**：代码把整章拆成场景，写 `chapters/<章>/chapter.json`（场景顺序、本章 CG 描述）和各 `<场景ID>.nvs`。任务到章粒度，中断整章重跑。

## 审稿（分两档）

- **角色/模型**：审稿（主模型），工具循环，可查证据。分两档：忠实度检查默认开，只查漏段、加戏、对白改写、说话人归属错、独白降级、顺序不连贯、设定冲突；文风审稿保留作品开关、默认关，只评文笔，不评情节结构。两档的提示词都写明评什么、不评什么（忠实度档不评文风，文风档不评结构和情节）。
- **输入/行为**：对照原文和设定集，只列有把握的问题，定位到句子；不读全书，用工具按需查原文段落、术语出现在哪里、某一章的摘要。
- **输出契约**：`{ issues: [{ type, severity: "minor" | "major" | "critical", quote, sourceRef: { chapterId, paragraphStart, paragraphEnd }, evidence, suggestion }] }`；`type` 从缺陷分类里取：对白忠实 / 说话人归属错 / 独白降级 / 漏段 / 加戏 / 顺序不连贯 / 设定冲突 / 文风 / 动机。每条问题必须逐字引用原文段落（`quote`），代码核对 `quote` 确实出现在 `sourceRef` 指的原文段落里，对不上打回重交。
- **后续**：两档都不循环——写手按问题改一遍，改完不再复审。

## 演出与图清单

- **角色/模型**：美术导演（主模型），工具循环，有请求次数预算（占位默认 30，待测试用书到后校准；超限先提醒再硬停，见「Settled & ruled out」）。一章跑一个循环：读整章剧本，用补丁工具插入演出指令（背景、镜头、CG、粒子、滤镜），然后列出本章的图清单。
- **输入**：整章剧本、设定集切片（本章出场的角色、地点及其已登记的造型、表情、变体）、已有素材清单。
- **输出契约**：演出补丁 + `ImageManifest` 图清单。清单每项只填素材名（如 `lin-xiao/uniform/angry`、`classroom/dusk`）、类型（立绘 / 背景 / CG / 表情差分 / 背景变体）和一句画面描述。是否已有、派生自哪张基准图由代码按素材名和已登记素材算出，模型不填；CG 项的一句画面描述由代码聚合写进 `chapter.json` 供场景画师使用。
- **同义表情合并**：列清单时，写手写出的未登记表情先和已有表情比对，意思相同就改用已有的表情名，不新画；确认是新表情才登记进清单。
- **持久化**：图清单存 `project.db` 任务结果里；要新画的项进入出图队列。
- **补丁工具** `apply_staging_patch { patch }`：一个字符串参数，行锚点补丁。读场景时返回带行号的文本，模型按行号写补丁，四种操作：`PUT <N:`（在第 N 行前插入）、`PUT >N:`（在第 N 行后插入）、`PUT N.=M:`（把第 N 到 M 行换成新行）、`CUT N`（删掉第 N 行），每个操作符后面写补丁后的新行。解析器校验补丁格式和行号，错了列出合法写法退回；美术导演循环里 `.nvs` 是独占的，不需要防并发。编辑器的场景重写不用这个工具，仍走整场新文本加句子 ID 差异。
- **循环进度持久化**：已插的补丁、已定的图清单进度写进 `apply_staging_patch` / `submit_image_manifest` 的工具结果 `details` 或 `custom` 会话条目；上下文压缩后由代码从这些条目重建进度，不靠摘要器记。

## 出图

- **角色/模型**：三个画师，各跑工具循环，由代码按出图队列调度：同一张图只画一次，基准图画完它的差分才开始画，同时画的图不超过「同时出图数」（默认 8）。
  - 立绘画师（主模型）：造型基准图，竖版透明底。
  - 场景画师（主模型）：背景基准图和 CG，16:9，主体在 4:3 安全区。
  - 差分画师（快速模型）：表情差分和背景变体，从基准图编辑派生，只改一处。
- **输入**：代码把一项任务需要的东西都放进上下文：图清单里的一项（素材名、类型、一句描述）、对应的设定集字段（角色外貌和造型、地点描述）、风格描述；派生图另附基准图。画师不用工具去查。所有画师调用都把画风参考（主视觉加最多 2 张补充参考，排在最前面）作为参考图带上；场景画师画 CG 时，由工具代码把出场角色的外貌原文和颜色锁定句拼入提示词（画师只写内容段），并把出场角色的造型基准图和（有的话）地点基准图一并作为参考图（排在画风参考之后）。
- **提示词拼装**（详见 `docs/visuals.md` 2.4、2.5）：工具按固定顺序拼成一段文字——参考图声明 → 素材类型句 → 画师写的内容段 → 角色外貌（设定集原文）→ 画风描述（`style.json` 原文）→ 构图与输出约束 → 颜色锁定句（立绘和 CG）→ 画风固定句（最后一行）。除内容段外都是代码写的，固定句是 `creator` 包里的英文常量。
  - 立绘/造型基准图：内容段写姿势和表情；构图约束是从头顶画到膝盖上方，腿在膝盖上方被画面底边裁断，人物居中，头顶留少量余量，竖版透明底、半透明边缘颜色和相邻衣服或皮肤一致。
  - 背景：内容段写地点和变体的可见要素；约束是 16:9、主体在中间 4:3 安全区、空景。
  - CG：内容段写 `chapter.json` 里 CG 描述的可见画面；外貌由代码拼入；约束同背景。黑暗场景的 CG 默认用光影、剪影、留白来表现暴力和死亡，直白的内容交给文字；降敏改写仍作审核被拒后的兜底。
  - 画师只写内容段：看得见的东西，陈述句，不写画风、画质、构图词（工具查禁词，命中退回），不写否定句和 `Avoid:` 行。尺寸、透明底、参考图、用生成还是编辑接口，都由工具按素材类型和派生关系决定。
- **生图工具** `draw_image { content }`：一次任务只画一张图，素材由代码绑定，模型不填素材名。工具内部依次做：查禁词（命中就直接退回画师，不出图）→ 按素材类型定尺寸和背景、取参考图（差分和变体走编辑接口）→ 拼提示词（2.4 的顺序；视觉审核的 feedback 和审核拒绝的固定句放在内容段之后）→ 出图（`openai` SDK）→ 本地技术检查（解码、尺寸归一、透明底；派生图必须和基准图同尺寸，不符拦下重画）→ 视觉审核（视觉模型看图，输出结构化结果 `{ pass, failedChecks: [identity | anchors | description | style | artifacts], feedback }`，其中 `anchors` 同时核对 `keyColors`；CG 含已登记角色时，`identity` 一项拿 CG 比对所含角色的造型基准图，不比对设定图）→ 通过就存文件。然后把“通过”或“不通过和原因”交回画师，由它只改内容段里相关的那一句再画；重画次数由代码计数，用完「生图失败重试次数」（默认 3）就结束循环，用占位图并标“需要处理”。
- **审核拒绝**：画师内置提示词里写降敏规则——去掉武器、血、身体部位、年龄这类具象词，改成光影、氛围、剪影描述；角色描写用外观特征不用年龄词。被内容审核拒绝时，由工具把“上一次被内容审核拒绝，请收敛描写”固定句追加进重画 prompt 再生成一次，还被拒才用占位图并标“需要处理”。重试这一次走新 run，不沿用旧尝试的审核拒绝状态；task 行可以复用，重画计数清零。
- **持久化**：每张通过检查的图立即写 `assets/...` 并本地处理（转 WebP、放大）；任务记到图粒度，停止后重跑时跳过已有的图，只补没画完的。图片默认存为有损 WebP（质量 90，保留透明通道），应用设置里的全局开关可改无损。画师写的提示词和工具补上的参数存在 `project.db` 任务结果里（供重生成和改写时参考），不进作品文件。

## 编辑器：重写场景（差异列表）

- **角色/模型**：写手（写作模型），单次调用。材料由代码准备。
- **输入**：当前 `.nvs` 全文（带行尾句子 ID）、创作者指令、本场原文范围对应的原文、设定集切片、改编设置、本场涉及素材名清单。
- **输出契约**：整场 `.nvs` 新文本（不是 patch）。按 `decisions.md`「剧本 ID 与素材命名」，模型改写已有行时保留原行尾 ID，新写的行不带 ID。应用按句子 ID 比对新旧两版生成差异列表（ID 相同的标“修改”，旧 ID 消失的标“删除”，没有 ID 的标“新增”），给创作者勾选；勾选的行写入文件，新增行保存时补 ID。
- **校验/修复**：新文本解析失败，或出现原场景里没有的 ID、重复 ID → 错误还给模型，同写剧本。
- **持久化**：直接写 `.nvs`；修改历史记到 `project.db` 的持久条目清单（何时改了哪句、改成什么），不持久快照；撤销只在本次打开内有效，按逆操作回放。

## 编辑器：按选中原文修改

- **角色/模型**：写手（写作模型），单次调用。和重写场景同形态，指令换成“按这段原文改这个场景/这几句”，额外给选中段落和它在场景里的位置。
- **输出契约**：整场 `.nvs` 新文本，同样走差异列表勾选。

## 作品级对话面板

- **角色/模型**：主控（主模型），工具循环 `Agent`。创作者会连续讨论、翻设定、跨多轮攒提议。
- **上下文**：系统提示（作品信息、改编设置摘要、可用工具列表、当前位置：编辑器/设定集页传进来的章节或条目）+ 持久化的历史消息。工具按需取数据，不把整个工程塞进上下文。
- **工具**（每个都是 `AgentTool`，`parameters` 用 pi-schema）：
  - `read_chapter_preview` `{ chapterId }` → `ChapterPreview`
  - `read_bible` `{ scope?: "series"|"volume"|"work", chapterId?: string }` → 设定集切片（`chapterId` 用来截“截至本章”）
  - `read_glossary` `{}` → 术语表
  - `read_scene` `{ chapterId, sceneId }` → `.nvs` 文本 + 段落对照
  - `read_source_range` `{ chapterId, fromParagraph, toParagraph }` → 原文段落
  - `list_assets` `{}` → 已登记素材清单（查素材名用）
  - `read_chapter_manifest` `{ chapterId }` → 该章图清单（已有/新画、状态）
  - `read_task_result` `{ taskId }` → 任务结果和失败原因
  - 提议工具，一件事一个工具，模型只填要改什么和理由；条目路径、影响哪些章节、修改记录由代码算：
    - `propose_bible_change` `{ entryId?, changes, reason }`：改设定条目，不填 `entryId` 就是新增；`changes` 是条目字段的 pi-schema 结构
    - `propose_glossary_change` `{ term, changes, reason }`
    - `propose_adaptation_notes` `{ text, reason }`：改改编要求
    - `propose_redo_chapter` `{ chapterId, instruction }`
    - `propose_rewrite_scene` `{ chapterId, sceneId, instruction }`
    - `propose_redraw_image` `{ asset, instruction }`
    - `propose_resynthesize_volume` `{ volumeId, instruction? }`：以上每个都登记一条提议并返回提议 ID
  - `spawn_agent` `{ role, task, context }`：派子 Agent（角色从可用花名册里选，见 `pi-scaffolding.md` 通用层 5）
- **提议模型**：提议以确认卡形式展示，存 `project.db`，字段：`id、作品、kind、target（条目 ID/章节 ID/字段路径）、patch JSON、reason、feedback、状态、对话消息 ID（可空——确认点 1 的候选提议不走对话）、创建时间`。发起工作流前先出确认卡，写清要做什么、影响哪些章节，确认后才开始；`redo_chapter` 确认后该章进制作队列，但原章还没做完（queued / running）时提议直接拒绝。提议和修改历史挂钩：应用一条提议 = 一次可撤销的修改记录。创作者拒绝时可填理由写进 `feedback`，作为工具结果文本回给主控，让它知道为什么被拒而不是换个说法再提一遍。`kind` 除 `propose_*` 各值和 `add_text_marker`（编辑器横幅确认，不进面板）外，还有 `pick_character_design` / `pick_main_visual`——确认点 1 的角色设定和主视觉候选也借提议表存。
- **会话持久化**：每部作品可以有多个会话。消息存成 `id`/`parentId` 条目树进 `project.db`，改写一条消息后重新发送会形成分支；超过上下文时把较早的轮次压缩成摘要条目（已有摘要就增量更新），最近若干轮保留原文。
- **停止/恢复**：面板消息不进制作队列的停止语义；创作者中途关面板，下次打开从 `project.db` 重建 `Agent` 状态接着聊。
