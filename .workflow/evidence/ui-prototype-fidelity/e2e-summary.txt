Root cause 1 — m4-gate.spec.ts:154 click timeout (选择主视觉)
  The 30s click timeout does not measure UI responsiveness — it embeds the ENTIRE
  replayed production pipeline latency from 开始制作 to visual-confirm gate, because
  the link only exists once the pipeline reaches confirm point 1.
  Measured on a quiet machine with an instrumented probe (throwaway spec, since
  deleted — tests/e2e/zz-probe.spec.ts, never committed):
    link attaches T+24.9s after 开始制作  (83% of the 30s budget already consumed)
    the click itself then completes in 41 ms — element is perfectly stable
    (902 consecutive animation frames sampled: bounding box NEVER changes, element
    never detached/recreated — disproving any animation/remount instability theory).
  Under memory pressure/CPU contention (load average was 13.5 on a 16-core box during
  run B; the maintainer reports repeated OOM this round) the pipeline inflates past
  30s and the click times out with the misleading 'waiting for element to be visible,
  enabled and stable' tail line.
  This spec region (lines 137–160 incl. the 30s click) is BYTE-IDENTICAL to main
  3a8ba3b (diff verified empty); packages/creator (the pipeline) is untouched by
  ui-prototype-fidelity. Round-4's pass at workers=4 reflects a quieter machine.
  => pre-existing test-timing fragility on main, exposed by machine load. NOT a
  selector migration and NOT a product bug — per instructions not fixed, reported.
  (If the maintainer wants margin, the correct fix is a test-side timeout bump or
  splitting the wait into 'gate reached' + 'click', which is out of my edit scope.)
